# Feature Specification: 台股每日推薦與命中率初測

**Feature Branch**: `chore/spec-kit-setup`

**Created**: 2026-09-28

**Status**: Draft

**Input**: User description: 建立現有 tick-stock-panel 的台股每日推薦與命中率初測功能規格，讓使用者能看到固定時間產生的 Top 10 候選、保存不可變當日快照，並以 1D、5D、20D 實際交易日追蹤後續報酬與命中率。

## User Scenarios & Testing

### User Story 1 - 查看今日正式推薦 (Priority: P1)

使用者在 Dashboard 開啟產品後，可以直接看到最近一個已完成交易日的每日推薦狀態與候選股。每檔候選顯示股票代號、名稱、資料基準日、基準價格、排名、分數與簡短的客觀入選原因，並能進入個股資料查看既有行情與研究內容。

**Why this priority**: 先讓使用者能實際看到並理解「今天選了什麼」，才有後續檢驗命中率的價值。

**Independent Test**: 在已有一個可用交易日資料的環境中，等待或觸發一次既有盤後流程，開啟 Dashboard，確認最多顯示 10 檔、欄位完整、排序與後端結果一致，且能開啟選股復盤詳情。

**Acceptance Scenarios**:

1. **Given** 最近交易日的必要資料已通過資料健康檢查，**When** 固定盤後執行時間完成每日推薦，**Then** Dashboard 顯示該交易日的正式推薦快照與最多 Top 10 候選，並標示資料基準日與結果狀態。
2. **Given** 條件通過但沒有任何標的符合既有選取門檻，**When** 每日推薦完成，**Then** 系統顯示「資料可用、今日 0 檔候選」，不把 0 檔誤顯示為資料失敗，也不以舊日期結果代替。
3. **Given** 使用者點選某檔推薦，**When** 進入候選詳情或選股復盤，**Then** 可看到同一份快照中的基準價格、排名、分數與入選原因，不因最新行情刷新而改變原始推薦內容。

---

### User Story 2 - 追蹤推薦後的客觀結果 (Priority: P1)

使用者在每日推薦或 Selection Review 頁面，可以看到每檔股票在推薦後第 1、5、20 個實際交易日的報酬狀態與結果，並看到各期間的可評估數量、平均報酬與命中率。

**Why this priority**: 功能的核心目標是用可重複的資料檢查推薦結果，而不是只展示當下的排名。

**Independent Test**: 使用固定的推薦快照與固定的後續行情樣本，分別模擬尚未到期、已到期且有行情、已到期但缺行情三種狀態，確認 1D、5D、20D 的狀態、報酬與命中率分母正確。

**Acceptance Scenarios**:

1. **Given** 某推薦日後尚未累積足夠交易日，**When** 使用者查看結果，**Then** 對應期間顯示「追蹤中」，不顯示 0% 報酬，也不納入命中率分母。
2. **Given** 某標的已累積完整的 H 個實際交易日且價格資料可用，**When** 系統計算 H=1、5 或 20 的結果，**Then** 報酬以快照保存的基準價格與第 H 個交易日價格計算，並顯示完成狀態。
3. **Given** 期間已到期但標的價格、交易日證據或必要公司行動資料不足，**When** 系統更新結果，**Then** 顯示「不可評估」與原因，不略過缺口、不把下一筆可得行情當成該期間結果。
4. **Given** 一個期間有 N 筆完成評估，其中 P 筆報酬嚴格大於 0%，**When** 顯示命中率，**Then** 命中率為 P/N × 100%；未完成或不可評估資料不進入 N。

---

### User Story 3 - 確認推薦是否具備正式資格 (Priority: P1)

使用者可以辨識當日結果是正式可用、資料可用但 0 檔、尚未完成或不可用。若必要 DataHealth 或行情證據未達門檻，系統必須說明阻擋原因，避免使用者把不完整資料當成正式推薦或命中率樣本。

**Why this priority**: 台股金融資料缺口若被隱藏，會直接破壞推薦公平性與後續統計可信度。

**Independent Test**: 用資料健康檢查通過、資料健康檢查失敗、行情更新失敗、公司行動覆蓋不足及結果衝突的 fixtures，確認每一種狀態都不會產生可誤認為正式結果的推薦快照。

**Acceptance Scenarios**:

1. **Given** 必要資料健康門檻或當期行情／交易日／公司行動證據未通過，**When** 到達每日執行時間，**Then** 系統記錄當次嘗試為不可用，顯示具體阻擋原因，且不建立可供命中率統計的正式推薦名單。
2. **Given** 每日推薦流程在同一交易日重試，**When** 原始正式快照已存在，**Then** 重試回傳或讀取同一快照，不重新排名、不以更新後行情覆寫原始候選。
3. **Given** 發現相同推薦日出現不同內容，**When** 系統處理該衝突，**Then** 保留原正式快照、記錄衝突狀態，並將該次結果標為不可作為正式結果，不能靜默選取其中一份。

---

### User Story 4 - 重現當時的選擇理由 (Priority: P2)

使用者可以從歷史快照回看某一天的推薦依據，理解當時使用的規則版本、資料截止時間、候選排序與客觀訊號摘要；AI 文字若存在，只能作為說明，不能改寫或決定報酬結果。

**Why this priority**: 可重現性是公平比較命中率與發現資料問題的必要條件，但可在 P1 的每日推薦與結果追蹤之後提供完整檢視。

**Independent Test**: 讀取一份已保存快照，於後續行情或摘要更新後再次開啟，確認快照欄位、排序、分數、原因與資料日期仍一致，且結果計算只追加評估資料。

**Acceptance Scenarios**:

1. **Given** 某日正式快照已保存，**When** 使用者開啟該日詳情，**Then** 可以看到該日的模型／規則版本、資料截止時間、基準價格、排名、分數、訊號摘要及資料健康狀態。
2. **Given** 後續行情或公司行動資料被刷新，**When** 使用者再次查看同一快照，**Then** 原始推薦欄位維持不變；只在符合評估條件時追加對應期間的結果或明確的資料狀態。
3. **Given** AI 摘要不存在、失敗或內容與客觀訊號不同，**When** 使用者查看推薦，**Then** 推薦與命中率仍以結構化 Quant／行情資料為準，AI 不可阻擋或改寫正式結果。

### Edge Cases

- 非交易日、週末、休市公告日或交易日證據未確認時，不產生新的正式推薦，也不把最近舊快照標成今日推薦。
- 盤後刷新尚未完成、只完成部分交易所或資料日期落後時，當次結果顯示不可用或等待中，不能以部分市場資料冒充完整推薦。
- 可用資料通過但候選少於 10 檔時，顯示實際數量；Top 10 是上限與目標，不保證每天有 10 檔。
- 某檔缺少名稱、基準價格、必要特徵、排名或分數時，不建立缺欄位的正式候選；缺失原因需可見。
- 推薦日後標的停牌、下市、缺少某一實際交易日價格或公司行動證據時，該期間為不可評估，不把下一筆行情向前填補。
- 後續行情被修訂或重整時，不能修改快照中的原始基準價格、排名、分數、原因或資料截止時間；若結果驗證出現差異，保留可辨識的資料狀態。
- 既有行情資料庫沒有足夠暖機交易日或 DataHealth 尚未達每日因子計算門檻時，顯示不可用原因，不改用歷史 OOS 結果代替當日推薦。

## Requirements

### Functional Requirements

- **FR-001**: 系統 MUST 在每個有明確交易證據的交易日，於既有盤後資料更新成功後的固定時間點產生一次每日推薦嘗試；固定時間預設為台灣時間 16:30，並顯示實際執行與資料截止時間。
- **FR-002**: 系統 MUST 只使用推薦資料截止時間以前已可取得的行情、Quant 特徵、選股訊號、交易日證據與必要公司行動資料，不得使用後續行情、後續修訂欄位或事後排名結果。
- **FR-003**: 系統 MUST 沿用既有 Quant／selection 的單一權威選取與排序結果；第一階段不得新增另一套獨立選股規則、權重、門檻或前端重排邏輯。
- **FR-004**: 系統 MUST 以 Top 10 為顯示目標與上限，允許實際候選少於 10 檔或為 0 檔；「資料可用且 0 檔」與「資料不可用」 MUST 是不同狀態。
- **FR-005**: 每檔正式候選 MUST 保存股票代號、股票名稱、資料基準日、基準價格、排序、分數及客觀入選原因摘要；快照 MUST 另保存能辨識規則／模型版本、資料截止時間、資料健康狀態與必要訊號摘要的欄位。
- **FR-006**: 每日正式推薦 MUST 建立不可變的當日快照。相同推薦日的重試 MUST 是冪等讀取或明確衝突，不得因後續行情刷新、排名重新計算或名稱變更而覆寫原始候選內容。
- **FR-007**: 系統 MUST 在產生正式推薦前檢查既有 DataHealth 必要門檻，以及當期行情覆蓋、交易日證據、因子暖機與必要公司行動覆蓋；任一必要門檻未通過時 MUST 不建立正式推薦名單，並顯示阻擋原因。
- **FR-008**: DataHealth 的「尚未查詢、partial、stale、unavailable、blocked」狀態 MUST 不得被轉成 ready、0 分、0% 報酬或正式 0 檔推薦。只有完整檢查通過且候選為空時，才可顯示可用 0 檔。
- **FR-009**: 系統 MUST 以實際交易日計算推薦後 1D、5D、20D；每一期間的終點是推薦日後第 H 個已確認交易日收盤，不能以自然日或遇到缺口時的下一筆資料替代。
- **FR-010**: 第一階段報酬 MUST 以快照保存的基準價格與對應期間終點價格計算，沿用既有價格／公司行動語意，並明確標示為紙上、價格標準化報酬，不包含交易成本、滑價、股利總報酬或成交保證。
- **FR-011**: 單檔命中 MUST 定義為該期間可評估且未四捨五入的報酬率嚴格大於 0%；等於 0% 或小於 0% 均不算命中，pending 與 unavailable 不納入命中率分母。
- **FR-012**: 每個期間 MUST 顯示至少可評估數、追蹤中數、不可評估數、命中率與平均報酬；沒有可評估樣本時顯示尚無樣本，不得顯示 0% 命中率。
- **FR-013**: 系統 MUST 在 Dashboard 提供當日推薦摘要與狀態，在 Selection Review 提供歷史快照清單、單日明細與 1D／5D／20D 結果；兩處 MUST 使用同一份快照與結果口徑。
- **FR-014**: UI MUST 清楚區分正式可用、可用但 0 檔、追蹤中、不可評估、資料不可用與衝突等狀態，並顯示使用者可理解的原因；不得以 AI 文字判斷取代結構化資料狀態。
- **FR-015**: 每一份快照 MUST 足以重現當時為何入選，包括版本、資料日期／截止時間、候選排序、分數、原始客觀特徵或摘要、資料健康與來源狀態；後續評估資料只能追加，不能改寫原始推薦。
- **FR-016**: 系統 MUST 不提供自動下單、持倉模擬、資金配置、停損停利最佳化或獲利保證；UI 與說明 MUST 將結果標示為實驗性初測，不構成投資建議。

### Key Entities

- **每日推薦嘗試**: 某一交易日固定時間的處理結果，包含 available、blocked、pending、conflict 等狀態及阻擋原因；不可用嘗試不算正式推薦樣本。
- **每日推薦快照**: 某一推薦日的不可變正式候選清單與當時決策依據，包含資料基準日、截止時間、版本、候選欄位與健康狀態。
- **推薦候選**: 快照中的單一股票，包含代號、名稱、基準價格、排名、分數、客觀原因與後續各期間結果。
- **期間結果**: 某候選在 1D、5D 或 20D 實際交易日窗口的完成、追蹤中或不可評估狀態，以及可驗證的終點日期、價格與報酬。
- **命中率摘要**: 按推薦日與期間聚合的可評估樣本統計，包含命中數、分母、命中率、平均報酬與不可用／追蹤數，不代表投資績效或因果關係。

## Phase 1 明確包含

1. 既有盤後流程中的固定時間每日推薦嘗試，預設沿用台灣時間 16:30 與目前 live Quant 的單一規則版本。
2. 最多 Top 10 的正式推薦清單，允許少於 10 檔與可用 0 檔。
3. 不可變快照與可重現的推薦欄位：代號、名稱、資料日期、基準價格、排名、分數、客觀原因、規則／模型版本、資料截止與必要 readiness/provenance。
4. DataHealth 與當期行情、交易日、因子暖機、公司行動證據的 fail-closed 門檻及可見阻擋狀態。
5. 1D、5D、20D 實際交易日結果、單檔報酬、追蹤中／不可評估狀態、命中率與最小必要聚合統計。
6. Dashboard 的當日推薦摘要，以及 Selection Review 的歷史列表、單日詳情與結果追蹤。
7. 從快照回看當時選股理由的客觀摘要；AI 內容若存在只作輔助說明。

## 明確不包含

- 新的獨立選股策略、第二套 Quant scorer、策略調參、權重學習或自動最佳化。
- Historical Primary OOS、完整回測、walk-forward 研究平台或以歷史 OOS 取代當日 live 結果。
- 複雜投資組合績效、資金配置、交易成本／滑價模擬、風險調整績效、基準最佳化或獲利預測。
- 自動下單、券商連線、持倉同步與交易執行。
- 大型後台管理、批次人工編輯、任意日期重跑、手動改寫正式快照或匯入外部推薦名單。
- 把 AI 摘要、自然語言解釋或信心分數當成績效真值或命中判定依據。
- 以最新行情回填或覆寫過去快照，或把缺資料靜默轉成 0、最新值或下一筆行情。

## 尚未確定、真正會影響實作的問題

以下問題不阻止本規格採用目前的最小可行預設，但在進入 implementation 前需定案：

1. **正式推薦的最小 DataHealth 門檻**：本規格預設採每日因子計算所需的 readiness，加上當期 live 行情、交易日與公司行動證據；是否要提高到 `ready_for_training` 或 `ready_for_primary_oos`，會直接影響可產生推薦的交易日數與初期可用性。
2. **固定執行時間是否永久沿用 16:30**：本規格沿用既有盤後更新完成後的 16:30 Asia/Taipei 排程；若產品要改成其他時間，會影響資料截止、當日定義、重試窗口與 Dashboard 的「今日」判定。
3. **基準價格口徑是否維持收盤到收盤**：本規格預設使用推薦日基準收盤價，評估第 H 個交易日收盤；若要改成下一交易日開盤，需同步調整快照欄位、成交可得性說明、缺口處理與命中率口徑。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 在資料健康與必要來源均通過的交易日，使用者可於固定執行完成後 1 分鐘內在 Dashboard 看到該日正式狀態與最多 10 檔候選；資料不可用時同樣可看到明確阻擋原因。
- **SC-002**: 每一個正式推薦候選的必要欄位完整率為 100%，至少包含代號、名稱、資料日期、基準價格、排名、分數與客觀原因摘要。
- **SC-003**: 對任何已保存正式快照，於後續行情刷新、頁面重整或重試後，原始候選內容與排序維持 100% 一致；同一推薦日不產生兩份互相競爭的正式快照。
- **SC-004**: 對已成熟且資料完整的 1D、5D、20D 樣本，命中率可由畫面顯示的命中數與可評估數重新計算，結果差異為 0 個百分點；pending 與 unavailable 不進入分母。
- **SC-005**: 使用者可從 Dashboard 進入單日詳情，在 3 次操作內找到每檔推薦的原始基準價格、排名、分數、入選原因及 1D／5D／20D 結果狀態。
- **SC-006**: 資料不足、交易日未確認、結果未成熟與結果不可評估等狀態均不會被 UI 顯示成正式推薦、0% 報酬或 0% 命中率。
- **SC-007**: 第一階段不執行任何自動下單或交易動作，且所有推薦與績效畫面都清楚標示實驗性初測與不保證獲利。

## Assumptions

- 使用者是既有 tick-stock-panel 的單一主要使用者，第一階段不新增角色、權限或團隊協作流程。
- 預設的固定時間為既有台股盤後資料更新後的 16:30 Asia/Taipei；實際推薦資料日必須是已完成且可驗證的交易日。
- 預設沿用目前 current live Quant 的固定模型、特徵、排序、流動性與暖機門檻；第一階段不提供使用者調整這些規則的設定介面。
- Top 10 是上限與展示目標，不保證每天有 10 檔；資料可用但候選為空是合法結果。
